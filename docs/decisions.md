# Engineering decisions

| Decision / WHAT | WHY | HOW / WHERE | WHEN | WHO | TRADEOFF |
|---|---|---|---|---|---|
| Token windows: 400 tokens, 60 overlap | Keep policy context while fitting compact models | Tokenizer offsets preserve original text; page-local windows in `ingest.py` | Upload and evaluation | Search users and experimenters | Pages never merge; small pages create small chunks. Overlap repeats text. Configurable 32–500 tokens. |
| Supabase pgvector cosine search | Persist vectors and source documents across application restarts | Normalized Sentence Transformer embeddings are stored in `policy_chunks`; `match_policy_chunks` in `supabase.sql` performs the dense lookup | Upload, startup, and dense search | Policy readers and operators | Adds a Supabase request to live dense latency. FAISS remains only for the offline historical evaluator. |
| BM25 plus dense | Exact policy terms and semantic paraphrases need different signals | Independent top-20 lists; lowercase Unicode word tokens | Every hybrid query | Retrieval users | BM25 does not stem or expand synonyms; another retrieval pass costs time. |
| Reciprocal Rank Fusion, k=60 | Combine rankings without score calibration | Sum `1/(60+rank)` with ranks starting at 1 | After first-stage retrieval | Ranking consumers | Ignores original score magnitude; deterministic chunk-order tie break. |
| Cross-encoder on a bounded fused pool (five in the UI) | Joint query/passage scoring is expensive | Score only selected pairs, then return top 5; the engineering API still permits controlled experiments | Hybrid reranked queries | Search users | Relevant passages outside the cutoff cannot be recovered. Compare 5/10/20 empirically. |
| Persistent chunks, local BM25 cache, one process, one lock | Keep documents after restart without adding a separate lexical service | Supabase stores PDFs/chunks/vectors; `app.py` reloads chunks and rebuilds BM25 on startup, then serializes upload/search | Startup and API operations | Policy readers and operators | Queries queue and BM25 rebuild time grows with corpus size. A separate BM25 service is unnecessary at the 5,000-chunk limit. |
| CPU inference, four Torch threads | Make the default runnable without a GPU and benchmark settings explicit | Cached models; `TORCH_NUM_THREADS` override in `retrieval.py` | First load / inference | Local developers | No GPU optimization; machine-specific latency. Model download and cold start excluded from warm benchmark. |
| Page-level graded judgments | Keep labels valid across chunk-size experiments | First hit per labeled page counts; grades 1/2, duplicates earn no further credit | `evaluate.py` | Experiment readers | Measures page coverage through returned chunks, not exact answer-span coverage. Small synthetic fixture is not production validation. |
| Text-only PDFs, bounded inputs | Support the required format without OCR or extra parsers | PDF validation, page/text/upload limits; escaped UI text | Ingestion and rendering | Local demo users | Scanned PDFs rejected; not a hardened multi-tenant service. |
| Keep BM25 matches even when their scores are nonpositive | Tiny corpora can give common matching terms negative IDF | Filter by membership in BM25's existing term dictionaries in `retrieval.py` | Lexical search | Users uploading a single short document | Small extra scan; no false empty result due solely to score sign. Regression-tested with one chunk. |
| Import PyTorch before FAISS | Reversed native-library initialization crashed on the tested macOS wheels | Intentional import order in `retrieval.py` | Process startup | Local operator | Platform-specific compatibility detail; no replacement library required. |
| Answer-first interface | Nontechnical users need the relevant wording, not ranking diagnostics | `answer_excerpt` scores up to 24 two-sentence windows from the top three passages with the existing model; UI shows the selected verbatim excerpt and citation | After retrieval, before API response | Policy readers | Extractive selection, not generated synthesis or answer verification; nearby conditions can be omitted, so full sources remain expandable. Answer selection has separate timing. |
| Fixed user-facing defaults | Avoid asking policy readers to tune retrieval | UI always uses hybrid RRF + reranking, 5 candidates, 5 results, default 400/60 chunking; technical API/evaluator settings remain for experiments | Upload/search | Nontechnical users | Five won the small fixture, not every corpus; larger cutoffs require new evaluation. |

## Default selection research (2026-09-25)

[Sentence Transformers](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html) describes retrieving a candidate pool and jointly scoring query/passage pairs with a cross-encoder. Its example pool size is not a universal optimum. Our measured 5/10/20 comparison supports five for this local demo: best observed nDCG@5 and lowest reranking latency. No claim is made for untested 25/50-candidate pools.

[Unstructured's chunking guidance](https://unstructured.io/blog/chunking-for-rag-best-practices) recommends experimenting around 250 tokens and explicitly says the right size depends on documents. We retain 400 with 60 overlap: more room for policy conditions than very short fragments, with headroom below the current 512-token model limit for ordinary queries. Larger 500+ chunks risk truncation; much smaller windows may separate rules from exceptions. This is a reasoned default, not a measured global optimum. The short-page fixture cannot distinguish these larger window sizes.
